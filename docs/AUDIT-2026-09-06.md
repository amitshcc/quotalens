## 1. Launch blockers

A blocker is only: a false security claim, a number presented as certain that is
not, or a documented command that fails on a clean install.

### B1 · A hostile `spend.exponent` takes the whole dashboard to HTTP 500 — *number presented as certain* class, and a false "honest by construction" claim · **blocker** · effort S

- **Claim** (README §The dashboard): "States are honest by construction … if the
  response could not be parsed, every value is replaced by an em dash and the
  frame changes."
- **Reproduction**: upstream returns the normal payload with
  `spend.used.exponent: 60` (scratch fake, `POST /mode/m_exp`). The poll is
  accepted (`/api/poll` → `"state":"ok"`), the overage row is **stored** with
  exponent 60, and then:
  ```
  GET /               -> 500
  GET /api/health     -> 500  {"error":"internal error; see server log"}
  GET /api/quota/current -> 500
  GET /api/dashboard  -> 500
  GET /metrics        -> 200
  log: ValueError: implausible currency exponent 60   (parse.py:314, format_money)
  ```
  `quotalens status` in that state reports "process alive but /api/health did
  not answer".
- **Evidence**: `parse.py:328-349` (`_spend_from_spend_block`) passes any integer
  exponent through; the only guard is in `format_money` (`parse.py:311-314`),
  which is called at render time from `poller.py:146` (`spend.used_text` in the
  status dict) and `dashboard.py:426`. The stored row keeps the bad exponent
  (`overage` rows `(…,316,200,60)` observed), so `dashboard.py:426` can raise
  again for any range whose last overage row is that one.
- **Why a blocker**: one field of one payload turns every page and every JSON
  endpoint into a 500 for as long as the upstream sends it, which is the
  opposite of "every value is replaced by an em dash".
- **Smallest fix**: validate the exponent where the spend block is parsed
  (`_spend_from_spend_block` / `_spend_from_overage_endpoint`): out of `0..6`
  → `SpendReading` is `None` (spend unknown), and never store it. One `if`.

### B2 · `quotalens_session_headroom_percent` and `quotalens_burn_pts_per_hour` report a number for a lapsed or stale session window — *false "NaN, never a stale number" claim* · **blocker** · effort S

- **Claim** (README §When a window is not running): "`/metrics` reports `NaN` for
  the same cases, never a stale number somebody would alert on."
- **Reproduction A (lapsed)**: upstream keeps returning `five_hour` with
  `utilization 40` and a `resets_at` that has now passed (scratch fake
  `/mode/frozen`, 45 s ahead, then wait). Observed at 11:19:17Z:
  ```
  /api/quota/current: five_hour pct=None last_pct=40.0 current=False lapsed=True
  /metrics: quotalens_quota_percent{window="five_hour"} NaN
            quotalens_session_headroom_percent 60        <- 100 - 40, from the lapsed row
  hero:     "The session window ended at 11:19 and no new one has opened."
  ```
- **Reproduction B (per-window stale)**: upstream drops the `five_hour` block
  while `seven_day` and the Fable limit keep refreshing (`/mode/dropfive`),
  wait > 3 intervals. Observed at 11:27:39Z:
  ```
  /api/quota/current: five_hour pct=None stale=True; seven_day 99.8 current
  /metrics: quotalens_quota_percent{window="five_hour"} NaN
            quotalens_session_headroom_percent 73.5     <- from the stale row
            quotalens_burn_pts_per_hour 908.571         <- from the stale rows
  ```
- **Evidence**: `metrics.py:114-116` gates `quota_percent` on
  `window_has_lapsed` and `window_is_stale`; `metrics.py:131-133` gates

- **Smallest fix**: compute `live` once for the session row and reuse it for
  headroom and burn (two lines); the spend gauges (`metrics.py:178-182`) have no
  freshness gate at all and should take the collector one.

### F1 · The hero shows "74% left, resets in 2h 50m" from a session reading the meter beneath it has withheld as stale · **high** · S

- **Claim** (README): "a window whose own reading has gone unrefreshed for three
  poll intervals is withheld like any other unknown" and "the rule … lives in
  `compute_runway`, so every consumer inherits it".
- **Reproduction**: `/mode/dropfive` (block absent, neighbours healthy), wait
  > 3 × interval. DOM at 11:27:39Z:
  ```
  hero:  "Session | 74 | % left | resets in | 2h 50m | Collecting: 1m of samples.
          74% left, and the window resets in 2h 50m."
  meter: Session — (withheld) "last ok 11:23"
  /api/quota/current: five_hour stale=true pct=null
  ```
- **Evidence**: `dashboard.py:525-543` passes the collector-level `withheld` to
  `_burn_view` and only the meter's *state* (READOUT_OFF) for styling; the
  headroom and verdict are computed from `current.pct` regardless
  (`dashboard.py:1035-1038`). The comment at 522-523 says the hero "reads the
  session meter's own view: same tier, same withholding" — it does not. The
  2026-09-04 QA entry ("Session 40% used, resets 14:00 … twelve pixels below a
  hero saying no window") is the mirror image of this.
- **Fix**: pass `session_view.withheld` (not only its state) into `_burn_view`
  and treat it as `withheld`.

### F2 · The rule "never present a session percentage as current once its reset has passed" does not live in `compute_runway`; it is implemented twice, and two consumers reach past both · **medium** (doc + code) · S

- `runway.py:96-110` holds one copy; `dashboard.py:923-932` (`window_has_lapsed`)
  holds the other, and that is what `/api/quota/current` (`api.py:530`) and
  `/metrics` (`metrics.py:115`) import. `compute_runway` has exactly one caller
  (`dashboard.py:1035`, the hero). So the README's architectural sentence is
  false as written; the *outcome* holds for the hero, meter, ring, favicon,
  `/api/quota/current` and `quota_percent` (all observed in B2's repros: favicon
  `aria-label="QuotaLens — session window unknown"`, meter foot "ended 11:19").
- Consumers that reach past both: (a) `/metrics` headroom and burn (B2);
  (b) the webhook body's `headroom_pct` and `session_resets_at`
  (`poller.py:553-554, 568`) are taken from the freshly parsed reading with no
  lapsed check — a `burn_alert` firing while the upstream still reports a passed
  `resets_at` would POST a headroom for a window that has ended. Not triggered
  live (a flat lapsed window does not cross a burn threshold); by code reading.
  (c) `_burn_view` prefers the derived session table's end
  (`session[1]`, `dashboard.py:1034`) over the reading's `resets_at`; in a
  contrived case (reset moved *backwards* 10 min, `/mode/lapsed`) the hero said
  "resets in 2h 55m" while the meter said "ended 11:09". Low weight: the upstream
  is not known to move a reset backwards.
- **Fix**: README sentence → "lives in `window_has_lapsed` and `compute_runway`";
  gate the webhook headroom on `window_has_lapsed`.

### F6 · `quotalens stop` will SIGTERM, then SIGKILL, whatever process the pid file names · **medium** · S

- **Reproduction**: write the pid of an unrelated live process (the fake
  upstream) into `quotalens.pid` with a `quotalens.runtime.json`:
  `status` → "process alive (pid 8357) but …/api/health did not answer", exit 1;
  `start` → "not started: already running (pid 8357)", exit 1.

  kills `running_pid(pidfile)` with no check that the process is a QuotaLens
  server (no health probe, no cmdline or start-time comparison). pid files
  survive a reboot, so pid reuse is the realistic path.

  zombies and Windows handles but not reuse.
- **Fix**: record the process start time (or the `--port`) in
  `quotalens.runtime.json` at start and refuse to kill when it does not match;
  or require `/api/health` to answer before signalling.

### §3 Security claims, "merely wrong" sense

- Cookie reach: static inspection of the whole tree. Persistence is only
  `KeyringSecretStore` (`secrets.py:74-108`); `config.json` writes only
  `CONFIG_KEYS` (`config.py:255-360`, no cookie/host key); the `sample` table
  stores usage/overage bodies (`poller.py:349, 694`), never `/api/bootstrap`;
  logs go through `RedactingFilter` which rewrites `exc.args` so `repr(exc)` is
  scrubbed too (`secrets.py:191-193`); CLI error prints use
