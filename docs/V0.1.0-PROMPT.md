## Ground rules, unchanged from the kickoff

- The cookie lives only in `keyring`, redacted from logs, tracebacks and every
  API response. Nothing you add may weaken this — in particular the webhook and
  the export endpoints below are new places for account data to leak, so treat
  them as security surfaces, not features.
- Loopback only. No `--host`.
- No new runtime dependencies. `/metrics` is hand-rolled text; the webhook uses
  the HTTP client we already ship. If you think a task genuinely needs a
  dependency, stop and ask.
- Type hints throughout, `ruff check` clean, tests written alongside the code,
  no test touches the network.
- Small commits, one logical change each. Do not batch a stage into one commit.
- Batch your questions. Ask at stage boundaries, not every few minutes.

## Stage 1 — correctness, before anyone has data to corrupt

These two are the reason this session exists. Both are described with evidence
in `FEATURE-REVIEW.md` §2.4.

**1. `burn.is_reset` falls through to the percentage-drop rule unconditionally.**
The docstring says the drop rule covers payloads where `resets_at` is absent or
null; the code applies it even when both `resets_at` values are present and
unchanged. So a server-side downward correction of more than `RESET_DROP_PCT`
gets classified as a window boundary — and Anthropic has publicly confirmed
shipping exactly that kind of correction. Fix: fall through to the drop rule
only when at least one `resets_at` is missing. The wrong classification splits a
burn segment, truncates a session window, and writes a bad `session_window` row
that survives the rebuild, so add tests for all three consequences, not just for
`is_reset` in isolation.

**2. `sessions.rebuild` is O(all history) on every poll.** `poller._collect`
calls it each cycle; it reads the entire `quota` table, re-derives every window
from the beginning of time, then deletes and re-inserts the whole
`session_window` table. Fix: full rebuild at startup and after a schema
migration only; per poll, maintain the current and the previous window
incrementally. Keep the pure derivation function as-is and testable — the
incremental path must produce byte-identical rows to a full rebuild over the
same data, and I want a test that asserts exactly that on a generated series
with resets and gaps in it.

**3. Sample retention.** Unbounded `sample` growth is a bug in "leave it
running," not a post-1.0 nicety. Keep the last N samples plus every sample whose
top-level key set is novel (that set is our endpoint-drift record and must
survive pruning). Add a `quotalens prune` command and a documented default.
Prune on a schedule inside the poller too — a default nobody ever runs is not a
default.

## Stage 3 — the five features

In this order. Each is specced in `FEATURE-REVIEW.md` §5 with a rationale and a
rough size; if your implementation is coming out much larger than the estimate,
stop and tell me before you finish it.

**4. `--profile NAME`.** Namespaces the keyring username, the database filename
and the default port. Two accounts is two processes and two bookmarks — do not
build account switching inside one process. Make sure `start`/`stop`/`status`/
`logs` and the pid file are profile-aware, or the second profile will kill the
first one's server.

**5. `/api/export.csv` and `/api/export.json`.** Derived rows by default. Raw
`sample` rows only behind an explicit flag, carrying the same redaction warning
`probe` already prints. Stream rather than buffering a month of history.

**6. Burn-rate threshold alerts.** `Settings.burn_alert_pts_per_hour` already
exists and nothing detects the crossing. Detect it, write an `event` row, expose
`/api/events`, surface events on the dashboard, and fire an optional webhook.
Webhook rules: opt-in by config, one POST with a small JSON body, no account
identifiers and no cookie in it ever, a timeout, no retry storm, and a failure
that logs and is dropped rather than one that blocks or crashes the poller. Edge
transitions only — one event per crossing, not one per poll while over the line.

**7. `/metrics`.** Hand-rolled Prometheus text exposition. No
`prometheus_client`. Get the format details right (`# HELP`, `# TYPE`, label
escaping, one trailing newline) — a subtly malformed exposition is worse than
none because Prometheus will scrape it and lie.

**8. A reset-model watchdog.** The five-hour session boundary comes from
`resets_at − 5h`, which is our inference, not a published algorithm (§2.3). So
make it falsifiable rather than hedged: if `five_hour.resets_at` moves forward
by less than five hours without the percentage dropping, the fixed-window
assumption the whole session history rests on is wrong. Record an event and say
so on the page, plainly.

## Stage 4 — truth in the docs

Prose, but not cosmetic: each of these is a claim we currently make that the
review found to be false. Do them as their own commits so I can review wording
separately from code.

- **The Terms.** Replace the softened disclaimer with the actual clause.
  Consumer Terms §3.7 prohibits accessing the Services "through automated or
  non-human means, whether through a bot, script, or otherwise" except via an
  Anthropic API key or where otherwise explicitly permitted. There is no
  carve-out for reading your own usage. State it plainly, then state the two
  mitigating facts without dressing them up: no enforcement against read-only
  usage monitors is known, and this tool never sends a prompt or spends a token.
  Do not write "what every tool in this space does" or any variant of it. The
  reader is deciding whether to run this against their own account; give them
  the clause and let them decide.
- **`resets_at − 5h`.** Wherever it is stated as fact — the `burn.py` docstring,
  the README, and anything derived from `session_window` — mark it as our
  inference from observed behaviour and point at the watchdog from task 8 as the
  check on it. Anthropic has never published the anchoring algorithm.
- **`VISION.md`'s opening.** It claims nothing joins level and attribution.
  Claude Code's `/usage` now breaks recent usage down by skill, subagent,
  plugin, MCP server and scheduled task, on Pro and Max, officially, with no
  cookie — better than our planned M3. Rewrite the opening around what is
  actually unique and what the doc already says further down: **Claude tells you
  what's consuming quota right now, and then forgets. QuotaLens remembers.**
  Smaller claim, true claim.
- **The README's "what this doesn't do" section.** Per-project attribution,
  desktop notifications, non-loopback binding, Docker, reading Claude Code's
  OAuth credentials, other providers. Link to `ccusage` and `/usage` for
  attribution and to ClaudeUsageBar for a macOS menu bar. Pointing at the better
  tool is a feature.
- **The platform claim.** Until stage 5 is green, the README says "macOS and
  Linux; Windows untested."
- **An issue template** that tells people not to paste unredacted `probe`
  output. `PLAN.md` asked for it and it doesn't exist.
- **`PLAN.md`** gets a note at the top pointing at `docs/MVP-SCOPE.md` as the
  current scope, so the two don't silently contradict each other for the next
  reader. Do not delete M3 from it; mark it deferred with the reason.

## Stage 5 — release gates

Not features. Things that must be true before I tag anything.

- **CI.** GitHub Actions on `macos-latest`, `ubuntu-latest` and
  `windows-latest`: install from the built wheel, `ruff`, `pytest`, and a smoke
  run of `quotalens serve` against `qa/fake_claude.py` long enough to write rows
  and read them back. Cross-platform is our headline feature and it currently
  has no CI and no evidence it has ever run on Windows or Linux. That is a
  claim, not a fact, until three runners are green. Expect Windows to fail on
  paths, the pid file, signals and the keyring backend — fix what you can, and
  tell me plainly what needs a real Windows machine.
- **`service install` on a clean machine.** I'll run this myself; give me a
  checklist. If a fresh macOS LaunchAgent or a fresh systemd user unit can't
  poll for an hour without a keychain prompt, the fallback is to cut
  `service install` to *printing* the unit file and the command. A background
  service that silently reads no data is the worst bug report this project can
  generate.
- **Measure the `sample` table.** Run against the fake upstream long enough to
  extrapolate, and put a measured number in the README next to the retention
  default. The review's estimate is arithmetic, not a measurement — say which
  one the README is quoting.

## What "done" means

`pytest` and `ruff` pass on three runners from a wheel install. A fresh install
with `--profile work` and `--profile personal` runs two servers on two ports
against two keyring entries without either one noticing the other. A month of
simulated history leaves the poll cycle flat rather than growing, and the
`sample` table bounded. A server-side percentage correction with an unchanged
`resets_at` produces no new session window. `/metrics` scrapes clean,
`/api/export.csv` round-trips, and a threshold crossing fires exactly one event
and one webhook. And the README, `VISION.md` and the disclaimer each say
something I could defend line by line to someone who went and read the source.
