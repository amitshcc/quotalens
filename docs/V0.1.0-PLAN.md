## Stage 1 — correctness

### 1.1 `is_reset` falls through to the drop rule unconditionally

`burn.is_reset` returns `(prev.pct - cur.pct) > RESET_DROP_PCT` even when both
`resets_at` values are present and unchanged. Fix: reach the drop rule only when
at least one `resets_at` is missing.

Three consequences to test, not just the predicate:

| Consequence | Assertion |
|---|---|
| burn segment split | `split_at_resets` returns one segment across a −20 pt correction with a stable `resets_at` |
| session truncated | `derive_sessions` yields one window, `samples` counting every row |
| bad row survives rebuild | `rebuild` then `store.sessions()` has one row, and a second rebuild does not resurrect the split |

Where a `resets_at` is genuinely absent the drop rule still applies, so the
existing null-payload tests must stay green.

### 1.2 Incremental session rebuild

`poller._collect` calls `rebuild` every cycle; `rebuild` reads the whole `quota`
table and rewrites the whole `session_window` table.

- Keep `derive_sessions` exactly as it is: pure, total, tested.
- `rebuild(store, now)` stays the full pass. Called at startup and after a
  migration only.
- Add `rebuild_recent(store, now)`: read `quota` from the start of the previous
  window (minus a margin), derive over that tail, upsert only the windows whose
  `started_at` falls inside the tail. Older rows are never touched.
- `store.upsert_sessions()` alongside `replace_sessions()`.

**Equivalence test, as asked:** generate a series with resets, gaps and an idle
span; apply the incremental path sample by sample; assert the resulting
`session_window` rows equal a full rebuild's, field by field.

**Known limit, documented in the docstring:** the tail cannot see an expiry that
only appears before it. If `resets_at` ever jumped *backwards* to a value older
than the previous window, the incremental path would open a new group where the
full pass would extend an old one. The startup full rebuild is the correction,
and the reset watchdog (task 8) is what would tell us it happened.

### 1.3 Sample retention

- `store.prune_samples(keep_last=N)`: keep the newest N rows per source, plus
  the earliest row for every distinct top-level key set, then `VACUUM` when a
  meaningful number of rows went.
- The key set is the drift record, so it is computed at write time into a new
  `sample.keysig` column (schema v5) and backfilled once during migration.
  Computing it at prune time would mean parsing every stored payload.
- `quotalens prune [--keep N] [--dry-run]`.
- The poller prunes on a schedule (every `PRUNE_EVERY_S`, default 6h), because a
  default nobody runs is not a default.
- Default `keep_last`: 20 000 samples ≈ 7 days at 60s with two sources. The
  README quotes a **measured** file size next to it (stage 5), not arithmetic.

## Stage 3 — features

### 4. `--profile NAME`

A global flag, resolved before settings. Namespaces three things:

| | default profile | `--profile work` |
|---|---|---|
| keyring username | `claude.ai-session-cookie` | `claude.ai-session-cookie:work` |
| database | `<data dir>/quotalens.db` | `<data dir>/quotalens-work.db` |
| pid / log / runtime | `quotalens.{pid,log,runtime.json}` | `quotalens-work.{pid,log,runtime.json}` |
| default port | 8787 | 8788 + crc32(name) % 100 |

The pid file must be profile-aware or the second profile's `stop` kills the
first profile's server; that is the failure this design exists to prevent, so it
gets a test. `QUOTALENS_PROFILE` is honoured for the service unit.

Port derivation is deterministic (crc32, not Python's salted `hash`) and
documented. Two profiles can still collide by chance; the failure is a clear
bind error and `--port` overrides.

### 5. `/api/export.csv` and `/api/export.json`

- `?table=quota|events|sessions|overage`, default `quota`; `?hours=` window.
- Streamed with `StreamingResponse` over a generator, never buffered.
- `table=sample` requires `?raw=1` **and** returns the `probe` redaction warning
  as a header and, for JSON, as a field. Raw payloads are the one export that
  can carry identifiers.
- The cookie can never appear: samples are response bodies, not requests. A test
  asserts the cookie is absent from every export.

### 6. Threshold alerts → `event` + `/api/events` + webhook

- Edge detection in the poller: compute the burn rate after each successful
  poll; when it crosses `burn_alert_pts_per_hour` upward, write one
  `burn_alert` event; when it falls back below (with hysteresis, 90% of the
  threshold, so a rate hovering on the line does not chatter), write one
  `burn_cleared`. State is held in the poller, not re-derived, so a restart
  cannot double-fire.
- `/api/events?limit=&kind=` and events surfaced on the dashboard.
- Webhook: `QUOTALENS_WEBHOOK_URL`, opt-in, one POST, JSON body of
  `{event, ts, rate_pts_per_hour, threshold, headroom_pct, resets_at, url}`.
  No org id, no cookie, no account identifier. 5s timeout, no retry, failure
  logged and dropped. Fired from a task the poll does not await.

### 7. `/metrics`

Hand-rolled text exposition, `text/plain; version=0.0.4; charset=utf-8`:
`quotalens_quota_percent{window,label}`, `quotalens_burn_pts_per_hour{window}`,
`quotalens_window_resets_at_seconds{window}`, `quotalens_poll_success_total`,
`quotalens_poll_failure_total`, `quotalens_last_success_timestamp_seconds`,
`quotalens_up`, `quotalens_sample_rows`, `quotalens_spend_used_minor`.
`# HELP`/`# TYPE` once per family, label values escaped (`\\`, `"`, `\n`), one
trailing newline. A test asserts the grammar, not just the substrings.

### 8. Reset-model watchdog

Under the fixed-window model a new `resets_at` is at least five hours after the
old one: a window can only start at or after the previous expiry. So a forward
move of more than the jitter tolerance but *less than* five hours, with no drop
in percentage, falsifies the model. Record a `reset_model_violation` event with
both values and the delta, and surface it on the dashboard as a plain sentence.

## Four decisions I would have asked about

1. **CI cannot exercise the keyring.** Storing a cookie in CI needs either a new
   credential path (an env var — a security regression) or `keyrings.alt` (a new
   package). I chose neither: the smoke test constructs the app with the
   in-memory secret store the tests already use, so it exercises the poller,
   store, API and dashboard on all three platforms, and the README says plainly
   that the keyring backend itself is covered only by the platforms I have run
   on. **If you would rather have a CI-only `keyrings.alt` dev dependency, say
   so and it is a ten-line change.**
2. **Profile port derivation** is `8788 + crc32(name) % 100`. Deterministic and
   documented, but two profiles can collide. The alternative is requiring
   `--port` for every non-default profile, which is more predictable and less
   convenient.
3. **Retention default of 20 000 samples** is a guess until stage 5 measures it.
   The README will quote the measurement; the default may move with it.
4. **Webhook body** contains no account identifier at all, which also means it
   cannot tell two profiles apart at the receiving end. I added the dashboard
   `url` (loopback) so a receiver can distinguish instances by port. Adding the
   profile *name* would be more useful and is still not an account identifier —
   say the word and it goes in.
